# 直播桌宠

面向恐怖游戏直播场景的 Windows 桌面互动角色。它接收游戏画面、主播语音和直播弹幕，把不同来源的信号归一成统一事件，再通过本地规则、状态机和按需模型能力生成动作、表情、气泡与语音回应。仓库还保留了主播表情感知实验，但该能力目前暂停启用。

**项目状态**：第一版核心链路已完成并经过离线、真人和真播验证

**开发周期**：2026-07—2026-08

**开发规模**：82 次提交

**项目角色**：个人独立完成（需求、架构、开发、调试、验证与文档）

**当前定位**：个人自用与求职技术展示，不是抖音官方玩法上架项目

> 本仓库是经过脱敏和裁剪的公开源码快照。角色私有美术帧、本人声纹、真实直播录制、密钥和历史提交没有公开；因此它适合阅读架构、运行离线验证和二次开发，但不是下载后即可完整还原作者直播画面的安装包。详见[公开仓库边界](#公开仓库边界)。

## 项目背景

普通桌宠通常只会循环播放动画，直播间挂件也容易变成“收到事件就立刻说一句话”的提示器。两者都缺少对直播上下文、主播状态和发言节奏的理解：

- 游戏突然出现惊吓画面时，角色应该快速反应，不能等大模型数秒后再说话；
- 观众集中进场、送礼或刷屏时，角色需要合批、分级和限流，不能盖住主播声音；
- 主播的语音指令拥有较高权限，普通弹幕不能直接控制桌宠；
- 复杂问题需要模型理解，但模型调用不能阻塞弹幕、动作和其他实时事件；
- 没有开播、摄像头或平台数据时，关键链路仍然应该可以复现和验证。

这个项目的目标不是简单叠加 AI 接口，而是把“能感知、会判断、能表现、可控制、可验证”做成一条稳定的实时互动链路。

## 目标用户与使用场景

### 目标用户

- 主要用户：使用 Windows 和抖音直播伴侣的恐怖游戏主播；
- 次要用户：希望研究桌面角色、多模态交互、实时事件系统或直播自动化的开发者；
- 当前产品边界：单主播、本地运行、个人自用，不处理多租户和平台级运营后台。

### 典型场景

1. **游戏惊吓反应**

   本地启发式检测画面亮度或音量突变，生成 `game.scare`，决策层立即选择惊吓动作、表情或短句，不经过慢速模型路径。

2. **观众进场与礼物答谢**

   弹幕采集层把真实平台数据归一为进场、聊天、礼物、点赞和关注事件。决策层根据粉丝牌、会员、守护、高价值礼物等信号分层，并通过合批、冷却和全局发言节奏控制回复密度。

3. **主播语音聊天与控制**

   麦克风输入依次经过 VAD、声纹验证、语音识别和唤醒窗口。通过验证的主播语音可以发起对话或控制指令；桌宠播放 TTS 时会发布“正在说话”状态，阻止麦克风把桌宠自己的声音再次识别成新问题。

4. **卡关攻略**

   主播触发攻略请求后，后台任务读取当前游戏上下文，按需搜索公开网页并让模型总结。没有可靠来源时明确拒绝编造攻略，任务处理过程不阻塞实时事件总线。

5. **开播会话与观众记忆**

   开播和下播命令界定一次直播会话。结构化观众信息、互动层级和必要的会话状态写入 SQLite；事实由代码生成和校验，不允许模型直接写入自由文本“印象”。

6. **主播表情互动（实验场景，当前暂停）**

   表情识别算法已用真实照片做过端到端验证，但它没有进入一键启动链路，实际直播中的摄像头来源和裁剪方式也尚未确定。因此代码保留供后续恢复，不计入当前可用能力。

## 需求拆解

### 功能需求

| 模块 | 需求 | 当前实现 |
| --- | --- | --- |
| 游戏感知 | 识别游戏场景、惊吓和卡关上下文 | 本地突变启发式负责低延迟惊吓；截图与多模态模型负责较复杂的场景理解 |
| 露脸感知 | 根据主播表情改变互动方式 | 算法与事件链路已独立验证，但未进入一键启动；直播摄像头来源和裁剪方案未定，当前暂停 |
| 弹幕感知 | 接收进场、聊天、礼物、点赞、关注和健康状态 | 通过 DouyinBarrageGrab 获取真实数据，解析后统一成 `danmaku.*` 事件；支持脱敏录制和离线重放 |
| 语音感知 | 只接受主播本人语音，并支持连续对话 | VAD、声纹验证、ASR、唤醒窗口和自发声抑制组成完整运行链路 |
| 决策 | 在实时性、角色感和安静边界之间取舍 | 规则快路径、异步模型路径、优先级、状态机、冷却、合批和防刷屏 |
| 表现 | 用角色动作、表情、气泡与语音呈现结果 | Electron 置顶窗口消费 `action.*`，驱动状态动画、气泡、TTS 和口型状态 |
| 控制 | 允许主播明确切模式、暂停、休眠和开关直播会话 | 本地控制面板、语音命令和受限弹幕关键词统一转换为 `command.*` |
| 记忆 | 跨互动保存必要事实，又不让模型污染数据 | SQLite 持久化结构化观众与会话数据，写入逻辑由代码控制 |
| 验证 | 无设备、无直播权限时仍能回归关键链路 | 已脱敏 fixtures、进程内 mock bus、真实数据回放和跨运行时 TCP 验证 |

### 非功能需求

- **低延迟**：惊吓、静音、休眠等确定性事件优先走本地规则；
- **不中断实时链路**：模型、搜索和 TTS 等慢任务放入后台队列；
- **可控发言**：角色不仅要会说话，还要有明确的闭嘴、冷却和降级策略；
- **权限隔离**：主播语音、房管/主播弹幕和普通观众输入拥有不同权限；
- **可恢复**：平台数据断流需要健康事件、告警、备用源和恢复路径；
- **可验证**：模块能独立运行，真实输入可脱敏录制后确定性回放；
- **本地优先**：事件总线、状态、记忆和控制面板均在本机运行，密钥只从本机环境读取。

## 整体架构

```text
┌──────────────────────────── 感知层 ────────────────────────────┐
│ 游戏画面       露脸实验       直播弹幕       麦克风             │
│ game.*         face.*        danmaku.*      audio.*           │
└──────────────────────────────┬─────────────────────────────────┘
                               │ perception.*
                               ▼
                    packages/contract
               统一信封、事件类型与载荷校验
                               │
                 ┌─────────────┴─────────────┐
                 ▼                           ▼
        本地规则快路径                 异步对话/模型路径
   惊吓、模式、限流、分层          搜索、攻略、复杂语义理解
                 └─────────────┬─────────────┘
                               │ action.*
                               ▼
┌──────────────────────────── 表现层 ────────────────────────────┐
│ Electron 角色窗口        动作/表情        气泡        TTS/口型 │
└────────────────────────────────────────────────────────────────┘
                               ▲
                               │ command.*
┌──────────────────────────── 控制层 ────────────────────────────┐
│ 本地控制面板       主播语音       主播/房管白名单弹幕           │
└────────────────────────────────────────────────────────────────┘

离线验证：fixtures → mock bus → brain → action
真实运行：Python / Electron → 127.0.0.1:8765 TCP JSON Lines 总线
```

### 1. 感知层

感知层只负责把外部输入变成标准事件，不决定角色最终要说什么或做什么。

- `services/perception-game/`：游戏截图、场景理解、惊吓检测与攻略上下文；
- `services/perception-face/`：人脸区域与表情信号实验；当前暂停，不在一键启动服务列表中；
- `services/perception-danmaku/`：平台数据采集、解析、归一、录制、重放和健康监测；
- `services/perception-voice/`：VAD、声纹、ASR、唤醒窗口和自发声抑制；
- `services/perception-ocr/`：已弃用的 OCR 实验模块，不进入默认运行链路。

### 2. 决策与对话层

`services/brain/` 是实时决策核心。它维护角色状态、事件优先级、回复层级、合批窗口、个人冷却和全局发言节奏。确定性事件直接生成动作；复杂语义任务交给 `services/dialogue/` 的后台队列，返回后仍由决策层校验和转换为动作。

这种双路设计避免两个极端：全部交给规则会让角色僵硬，全部交给模型又会增加延迟、成本和不可控输出。

### 3. 表现层

`apps/character/` 是 Electron 角色窗口，只消费 `action.*`：

- `action.play_motion`：切换动作状态；
- `action.set_expression`：更新表情；
- `action.show_bubble`：显示文本气泡；
- `action.speak` / `action.stop`：播放或停止语音，并同步口型与自发声状态。

表现层隐藏在事件契约之后，未来可以把帧动画换成 Live2D 或其他渲染方式，而不改感知和决策模块。

### 4. 控制层

`apps/control-panel/` 和受信任的语音/弹幕命令发布 `command.*`，包括静音、取消静音、休眠、唤醒、执行动作、切换模式、设置观众层级以及开始/结束直播会话。控制输入与普通聊天输入分开处理，避免任何观众都能直接控制桌宠。

### 5. 事件契约与传输

所有跨模块消息使用统一信封：

```json
{
  "channel": "perception.game.scare",
  "type": "game.scare",
  "ts": 1780000000.0,
  "source": "perception-game",
  "data": {
    "score": 0.91
  }
}
```

- `perception.*`：感知层发布，决策层消费；
- `command.*`：控制层发布，决策层消费；
- `action.*`：决策层发布，表现层消费；
- 离线测试使用进程内 mock bus；
- 真实运行使用 `services/bus/broker.py` 提供的本地 TCP JSON Lines 总线；
- 两种传输复用同一份 schema 和校验器，测试环境不另造协议。

完整类型与载荷见 [packages/contract/events.md](packages/contract/events.md)，架构约束见 [ARCHITECTURE.md](ARCHITECTURE.md)。

## 核心实现与设计取舍

### 低延迟规则与模型能力分流

惊吓反应、静音、休眠、模式切换等结果明确、时延敏感的事件直接走本地规则。攻略、复杂聊天和需要上下文归纳的任务才进入模型路径。这样既保留角色的即时性，也把模型用在真正需要语义理解的位置。

### 把“什么时候不说话”作为核心能力

直播互动最容易失败的地方不是不会回答，而是过度回答。项目同时实现了：

- 进场事件合批，避免连续逐个欢迎；
- 普通观众、高等级粉丝、会员/守护和高价值礼物分层；
- 同一观众冷却与全局语音间隔；
- 忙碌时从语音回复降级为气泡；
- `ACTIVE`、`QUIET`、`SLEEP` 等显式状态；
- 主播语音控制拥有更高优先级。

### 慢任务与实时总线隔离

网页搜索、模型请求和长文本生成通过后台工作队列执行。事件循环只做校验、排队和快速决策，避免一次慢请求拖住弹幕、动作和控制指令。Socket、SQLite 与共享状态都有明确的并发边界。

### 真实数据录制与确定性回放

平台数据格式与文档或测试样例经常不同。本项目曾在真播中发现 `Data` 字段是嵌套 JSON 字符串，随后把真实数据脱敏录制为 fixtures，并加入解析、归一和端到端重放验证。这样修复可以在不开播时重复验证，也不会把观众隐私提交到仓库。

### 语音闭环与自发声抑制

语音链路不仅包含识别，还处理了真实使用中更棘手的反馈回路：桌宠的扬声器声音会再次进入麦克风。TTS 开始和结束时发布 `audio.self_speaking`，语音感知据此暂停接收；再配合模型预热和常驻 TTS 进程，把真人实测稳态延迟降到约 6.2 秒，并停止自问自答。

### 结构化记忆，不让模型改写事实

观众等级、互动时间和会话状态由程序按 schema 写入 SQLite。模型可以读取经过筛选的上下文，但不能直接生成并持久化自由文本“用户画像”，以降低幻觉、隐私和长期数据污染风险。

### 直播采集兼容方案

透明 Electron 窗口在部分采集路径中会出现静帧。最终实测方案是：角色窗口使用不透明纯绿背景并关闭硬件加速，直播伴侣使用“窗口捕获”，再对该来源开启绿幕抠图。这样既能持续获取动态画面，也能在直播画面中去掉背景。

### 系统代理保护

弹幕采集依赖第三方抓取工具设置系统代理和本地根证书。`services/env-guard/` 在进入直播模式前记录环境，在正常退出时恢复，并为异常残留提供检查。恢复流程明确禁止强制杀死抓取程序，因为跳过清理可能让系统代理继续指向已停止监听的端口，造成整机看似断网。

## 技术栈

- **运行环境**：Windows、Python 3.11、Node.js、Electron；
- **消息通信**：`asyncio`、本地 TCP、JSON Lines；
- **视觉与音频**：MSS、NumPy、DeepFace、MediaPipe、Resemblyzer、edge-tts；
- **模型接口**：OpenAI 兼容对话接口、可配置多模态视觉接口；
- **数据存储**：SQLite、本地 JSON / JSONL fixtures；
- **工程方法**：事件契约、状态机、后台任务队列、真实数据录制回放、模块化验证。

## 本地运行

### 1. 环境要求

- Windows 10 / 11；
- Python 3.11；
- Node.js 与 npm；
- 运行视觉、语音或模型能力时，需要相应设备、网络和本机密钥；
- 真播弹幕链路还需要自行准备并评估 DouyinBarrageGrab 及其系统代理/根证书影响。

### 2. 安装依赖

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

Set-Location apps\character
npm install
Set-Location ..\..
```

部分深度学习依赖在 Windows 上对 Python 和 PyTorch 版本较敏感；遇到安装问题时按 [DEVELOPMENT.md](DEVELOPMENT.md) 的固定版本和 CPU 安装说明处理。

### 3. 配置本机环境

复制 `.env.example` 为 `.env`，按实际启用的模块填写：

| 配置 | 用途 | 是否离线验证必需 |
| --- | --- | --- |
| `PET_VISION_BASE_URL` / `PET_VISION_API_KEY` / `PET_VISION_MODEL` | 游戏画面多模态理解 | 否 |
| `PET_IMAGE_MODEL` | 可选的角色图像生成脚本 | 否 |
| `PET_CHAT_BASE_URL` / `PET_CHAT_API_KEY` / `PET_CHAT_MODEL` | 对话与攻略总结 | 否 |
| `PET_WAKE_WORD` | 主播语音唤醒词 | 仅语音对话需要 |
| `PET_GUARDRAILS` | 合规护栏开关 | 否 |
| `PET_MIC` | 固定麦克风序号或名称片段 | 仅实时语音需要 |
| `PET_VOICE_THRESHOLD` | 本人声纹相似度阈值 | 仅声纹验证需要 |

不要提交 `.env`、密钥、声纹文件或未经脱敏的真实直播数据。

### 4. 先运行离线验证

```powershell
.venv\Scripts\python.exe scripts\verify_contract.py
.venv\Scripts\python.exe services\brain\verify_brain.py
.venv\Scripts\python.exe services\perception-danmaku\verify_danmaku.py
.venv\Scripts\python.exe scripts\verify_integration.py
node apps\character\verify_character.js
```

这些检查不要求开播。模型、麦克风、摄像头和平台抓取相关的专项验证，需要相应外部条件。

### 5. 启动角色

公开仓库未包含作者的私有角色 PNG 帧。请先参考 [assets/character/ART_BRIEF.md](assets/character/ART_BRIEF.md) 准备兼容的角色素材，再运行：

```powershell
start-pet.cmd
```

需要接入真实直播时，请先完整阅读 [HANDOFF.md](HANDOFF.md) 中的开播顺序、弹幕健康检查、直播伴侣采集方式和安全红线。不要在不了解系统代理与根证书影响的情况下直接运行第三方抓取链路。
